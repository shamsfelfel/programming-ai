The problemالمشكلة

An order in this shop is a dictionary. It is built by hand in four different places in the file: the first counter, the second counter, the phone line, and the staff meal. Nobody wrote down what an order must contain, so each place writes what it remembers.

Diagnosisتشخيص العيب

There is no single answer to the question "what does an order contain?". The answer is scattered across four places, and every one of them is free to disagree with the others. Adding a field means finding all four by hand; forgetting one is not a mistake Python can detect, because to Python a dictionary with a missing key is simply a different, perfectly legal dictionary.

لا توجد إجابة واحدة لسؤال «ما الذي يحتويه الطلب؟». الإجابة موزَّعة على أربعة مواضع، ولكل منها حرية مخالفة البقية. فإضافة حقل تعني البحث عن الأربعة يدويًا؛ ونسيان أحدها ليس خطأً تستطيع بايثون كشفه، لأن القاموس الناقص المفتاح — في نظر بايثون — مجرد قاموس آخر مختلف وسليم تمامًا.

Step 1 — move the four construction sites into one __init__الخطوة 1 — انقل مواضع البناء الأربعة إلى __init__ واحد

You met __init__ in Lesson 1 as "the thing that fills in the fields". Now give it its real job: it is the only place an order can come into existence, so it is the only place that has to be right. Every attribute is set here — the ones the caller passes, the defaults, and the derived values nobody passes at all.

التقيتَ بـ __init__ في الدرس 1 على أنه «ما يعبّئ الحقول». الآن امنحه مهمته الحقيقية: فهو المكان الوحيد الذي يمكن أن يُولد فيه الطلب، وبالتالي هو المكان الوحيد الذي يجب أن يكون صحيحًا. كل خاصية تُضبط هنا — ما يمرره المستدعي، والقيم الافتراضية، والقيم المشتقة التي لا يمررها أحد إطلاقًا.

from datetime import date


class Order:
    def __init__(self, customer, discount=0):
        self.customer = customer
        self.discount = discount
        self.items = []
        self.paid = 0
        self.served = False
        self.created_at = date.today().isoformat()

    def add_item(self, name, price):
        self.items.append(name)
        self.paid += price

    def net_total(self):
        return self.paid - self.discount

Step 2 — the delivery fee, one line, one placeالخطوة 2 — أجرة التوصيل: سطر واحد في مكان واحد

Now make the same change that broke the dictionary version. Add a parameter with a default, assign it, and use it in net_total. Nothing at any call site has to change — the orders that pay no fee keep working untouched.

نفّذ الآن التعديل نفسه الذي عطّل نسخة القواميس. أضف معاملًا بقيمة افتراضية، وأسنده، واستخدمه في net_total. ولا شيء في أي موضع استدعاء يحتاج إلى تغيير — فالطلبات التي لا تدفع أجرة تواصل العمل دون أن تُمس.

from datetime import date


class Order:
    def __init__(self, customer, discount=0,
                 delivery_fee=0):
        self.customer = customer
        self.discount = discount
        self.delivery_fee = delivery_fee     # the new line
        self.items = []
        self.paid = 0
        self.served = False
        self.created_at = date.today().isoformat()

    def add_item(self, name, price):
        self.items.append(name)
        self.paid += price

    def net_total(self):
        return (self.paid - self.discount
                + self.delivery_fee)


sheet = [Order("Huda"), Order("Yousef", discount=1),
         Order("Amal", delivery_fee=3), Order("Kareem")]

prices = [("mango juice", 10), ("falafel plate", 8),
          ("orange juice", 7), ("hummus plate", 6)]

for o, (name, price) in zip(sheet, prices):
    o.add_item(name, price)

    print(o.customer, o.net_total())

One added line in __init__, one added term in net_total. There was no fourth site to hunt down, so there was no fourth site to miss.

سطر واحد مضاف في __init__، وحد واحد مضاف في net_total. لم يكن هناك موضع رابع يُبحث عنه، فلم يكن هناك موضع رابع يُنسى.

The trap hiding inside default valuesالفخ المتواري داخل القيم الافتراضية

Defaults just saved you. Now here is the one default that will betray you. It looks like the obvious way to let the caller pass a ready list of items:

القيم الافتراضية أنقذتك للتو. وهذه هي القيمة الافتراضية الوحيدة التي ستغدر بك. تبدو الطريقة البديهية للسماح للمستدعي بتمرير قائمة أصناف جاهزة:

class Order:
    def __init__(self, customer, items=[]):
        self.customer = customer
        self.items = items


huda = Order("Huda")
amal = Order("Amal")

huda.items.append("mango juice")

print("Huda  :", huda.items)
print("Amal  :", amal.items)
print("same list?", huda.items is amal.items)
Huda : ['mango juice'] Amal : ['mango juice'] same list? True

Never use a list or a dict as a default valueلا تستخدم قائمة أو قاموسًا كقيمة افتراضية أبدًا

Huda's mango juice appeared on Amal's order. The reason: items=[] is evaluated once, when the def line runs — not once per call. So there is exactly one list, created when the class was defined, and every order that does not pass its own list is handed that same list. They are not similar lists; they are the identical object, which is what is proves.

ظهر عصير مانجو هدى في طلب أمل. والسبب: items=[] تُقيَّم مرة واحدة عند تنفيذ سطر def — لا مرة لكل استدعاء. فتوجد قائمة واحدة بالضبط، أُنشئت لحظة تعريف الصنف، وكل طلب لا يمرر قائمته الخاصة يُسلَّم تلك القائمة نفسها. وهي ليست قوائم متشابهة، بل الكائن ذاته، وهذا ما يثبته is.

In a real shop this is not a curiosity — it is a juice billed to the wrong customer, and it gets worse all day as the one shared list keeps growing.

وفي محل حقيقي هذا ليس طُرفة — بل عصير يُحاسَب عليه العميل الخطأ، ويتفاقم الأمر طول اليوم مع تضخم القائمة المشتركة الواحدة.

You can watch the shared default swell up on its own, outside any class:

The fix is to default to None — an immutable value that cannot be shared and changed — and build a fresh list inside the body, which does run on every call.

والحل أن تكون القيمة الافتراضية None — قيمة غير قابلة للتغيير فلا يمكن تشاركها وتعديلها — ثم تبني قائمة جديدة داخل الجسم، الذي يُنفَّذ فعلًا في كل استدعاء.

class Order:
    def __init__(self, customer, items=None):
        self.customer = customer
        if items is None:
            items = []
        self.items = items

Why is None and not if not itemsلماذا is None لا if not items

An empty list the caller deliberately passed is falsy, so if not items would throw it away and silently substitute a different one. items is None asks the exact question you mean: "did the caller pass anything at all?"

القائمة الفارغة التي مررها المستدعي بقصد تُعدّ falsy، فـ if not items سترميها وتستبدلها بأخرى بصمت. أما items is None فتسأل السؤال المقصود بدقة: «هل مرر المستدعي أي شيء إطلاقًا؟»

Second example — a prescription at a clinicمثال ثانٍ — وصفة طبية في عيادة

Different domain, same principle. A clinic writes prescriptions. The course length is usually a week, nobody passes the dose log or the collection flag, and both must exist from the first moment — so __init__ sets all five attributes, and the list is built in the body, never as a parameter default.

مجال مختلف والمبدأ نفسه. تكتب العيادة وصفات طبية. ومدة العلاج أسبوع عادةً، ولا أحد يمرر سجل الجرعات أو علامة الاستلام، وكلاهما يجب أن يوجد من اللحظة الأولى — فيضبط __init__ الخصائص الخمس كلها، وتُبنى القائمة في الجسم لا كقيمة افتراضية لمعامل.

Why does def __init__(self, items=[]) leak items between objects?لماذا تُسرِّب def __init__(self, items=[]) الأصناف بين الكائنات؟

Default values are evaluated once, at definition time, and then stored on the function itself — which is why make.__defaults__ above showed the default list growing. The tempting wrong answer is the first: two separate lists with equal contents are not the same object, and the fixed version proves it — huda.items is amal.items printed False while both were real lists. Nothing is wrong with lists; the bug is that only one list was ever created.
القيم الافتراضية تُقيَّم مرة واحدة عند التعريف، ثم تُخزَّن على الدالة نفسها — ولهذا أظهر make.__defaults__ أعلاه القائمة الافتراضية وهي تنمو. والإجابة المغرية الخاطئة هي الأولى: فقائمتان منفصلتان بمحتوى متساوٍ ليستا الكائن نفسه، والنسخة المصحَّحة تثبت ذلك — إذ طبعت huda.items is amal.items القيمة False مع أن كلتيهما قائمة حقيقية. لا عيب في القوائم؛ العيب أن قائمة واحدة فقط أُنشئت أصلًا.

class MenuItem:

        self.name = name
        self.price = price
        self.category = category

        self.extras = []

        return f"{self.name}: {self.sold_today} sold"

Concept 2 — Instance attributes vs class attributesالمفهوم 2 — خصائص الكائن مقابل خصائص الصنف

The problemالمشكلة

Every menu item carries a VAT rate and the shop's name. Both are the same for all of them — the rate is set by law, and the shop has one name — but because they live in __init__ as ordinary parameters, they are typed out again for every single item.

كل صنف في القائمة يحمل نسبة ضريبة واسم المحل. وكلاهما متطابق في جميع الأصناف — فالنسبة يحددها القانون، والمحل له اسم واحد — لكن لأنهما يقيمان في __init__ كمعاملين عاديين، فإنهما يُكتبان من جديد مع كل صنف.

Four items, four copies of 0.05, four copies of the shop name. One of the four is typed as 0.5 — fifty per cent instead of five. The orange juice is overcharged every day and nobody notices, because nothing in the program ever compares the four copies to each other.

Conversion — state the shared fact once, on the classالتحويل — اذكر الحقيقة المشتركة مرة واحدة على الصنف

An assignment written directly in the class body, outside any method, creates a class attribute: one value stored on the class itself, which every object can read through self as if it were its own.

الإسناد المكتوب مباشرة في جسم الصنف، خارج أي دالة، يُنشئ خاصية صنف (class attribute): قيمة واحدة مخزَّنة على الصنف نفسه، يستطيع كل كائن قراءتها عبر self كأنها خاصته.

        self.name = name
        self.price = price

        return round(self.price * (1 + self.vat_rate), 2)

The gotcha: assigning through an object does not change the classالمصيدة: الإسناد عبر الكائن لا يغيّر الصنف

Reading self.vat_rate finds the class attribute. Writing juice.vat_rate = ... does something completely different: it creates a brand-new instance attribute on that one object, which from then on shadows the class attribute — hides it for that object only.

قراءة self.vat_rate تجد خاصية الصنف. أما الكتابة juice.vat_rate = ... فتفعل شيئًا مختلفًا تمامًا: تنشئ خاصية كائن جديدة على ذلك الكائن وحده، وتصبح من تلك اللحظة تحجب خاصية الصنف — تخفيها عن ذلك الكائن فقط.

    def __init__(self, name, price):
        self.name = name
        self.price = price

اقرأ السطرين الأخيرين بتمهّل. أُلغيت الضريبة على المحل كله، فامتثل طبق الفلافل، وبقي عصير المانجو يحاسب بـ 16% إلى الأبد. وسطرا __dict__ يوضحان السبب: فـ vat_rate موجودة الآن فعليًا على juice، فتجدها بايثون هناك ولا تنظر إلى الصنف مرة أخرى. سطر واحد بدا تحديثًا على مستوى المحل أنشأ بدلًا من ذلك استثناءً دائمًا.

The lookup rule, in one sentenceقاعدة البحث في جملة واحدة

Reading obj.x looks at the object first, then at the class. Writing obj.x = v always writes on the object; writing Class.x = v always writes on the class. So to change a shared value for everyone, you must name the class.

قراءة obj.x تنظر في الكائن أولًا ثم في الصنف. والكتابة obj.x = v تكتب على الكائن دائمًا؛ والكتابة Class.x = v تكتب على الصنف دائمًا. فلتغيير قيمة مشتركة للجميع عليك أن تسمّي الصنف.

Concept 3 — Methods that make the object speak: __str__ and __repr__المفهوم 3 — دوال تجعل الكائن يتكلم: __str__ و__repr__

The problemالمشكلة

The shop has Order objects now, but printing one gives a memory address instead of a receipt, so each shift wrote its own formatting helper. The morning shift wrote print_order_counter; the evening shift, not knowing about it, wrote print_order_receipt. The same order now prints two different ways depending on who is at the till, and a customer who comes back in the evening with a morning receipt is holding a document the evening printer cannot reproduce.

لدى المحل كائنات Order الآن، لكن طباعة أحدها تعطي عنوان ذاكرة لا فاتورة، فكتبت كل ورديّة دالة تنسيق خاصة بها. كتبت الورديّة الصباحية print_order_counter؛ وكتبت المسائية، دون علمها بالأولى، print_order_receipt. فالطلب نفسه يُطبع الآن بطريقتين مختلفتين حسب من يقف على الصندوق، والعميل الذي يعود مساءً بفاتورة صباحية يحمل وثيقة لا تستطيع طابعة المساء إنتاجها.

class Order:
    def __init__(self, number, customer):
        self.number = number
        self.customer = customer
        self.items = []


def print_order_counter(order):
    # written by the morning shift
    print(f"#{order.number} {order.customer}:"
          f" {len(order.items)} item(s)")


def print_order_receipt(order):
    # written by the evening shift, same data
    names = ", ".join(order.items)
    print(f"Order {order.number} for {order.customer}"
          f" [{names}]")

o.items.append("mango juice")
o.items.append("falafel plate")

print_order_counter(o)
print_order_receipt(o)

The object knows everything needed to describe itself, yet the description lives outside it — twice, in two functions that drifted apart the moment the second one was written. And print(o), the thing every Python programmer tries first, gives a memory address, which pushes the next person to write a third helper.

الكائن يعرف كل ما يلزم لوصف نفسه، لكن الوصف يقيم خارجه — مرتين، في دالتين تباعدتا لحظة كتابة الثانية. وprint(o)، أول ما يجربه كل مبرمج بايثون، يعطي عنوان ذاكرة، فيدفع الشخص التالي إلى كتابة دالة مساعدة ثالثة.

The 0x7f... part is where the object happened to sit in memory on that run. It is different every time the program runs, and different on your machine — which is the first clue that it is telling you nothing useful about the order.

الجزء 0x7f... هو الموضع الذي صادف أن يشغله الكائن في الذاكرة في ذلك التشغيل. وهو يختلف في كل مرة يُشغَّل فيها البرنامج، ويختلف على جهازك — وهذه أول إشارة إلى أنه لا يخبرك بشيء مفيد عن الطلب.

Step 1 — __str__: the line a human readsالخطوة 1 — __str__: السطر الذي يقرأه الإنسان

Define a method named __str__ that returns a string. Python calls it for you whenever the object has to become text: print(obj), str(obj), and inside an f-string. The two helper functions collapse into one method that lives with the data.

عرّف دالة باسم __str__ تُعيد نصًّا. وستستدعيها بايثون نيابةً عنك كلما احتاج الكائن أن يصبح نصًّا: في print(obj) وstr(obj) وداخل f-string. فتنطوي الدالتان المساعدتان في دالة واحدة تقيم مع البيانات.

class Order:
    def __init__(self, number, customer):
        self.number = number
        self.customer = customer
        self.items = []

    def __str__(self):
        return (f"Order #{self.number} — {self.customer}"
                f" — {len(self.items)} item(s)")

Step 2 — __repr__: the line a programmer readsالخطوة 2 — __repr__: السطر الذي يقرأه المبرمج

A container never calls __str__ on what it holds; it calls __repr__. The two have different jobs: __str__ is the customer-facing sentence, __repr__ is the unambiguous form you want when debugging — it should say the class name and the values that identify the object.

الحاوية لا تستدعي __str__ أبدًا على ما تحتويه؛ بل تستدعي __repr__. ولكل منهما مهمة مختلفة: فـ __str__ هي الجملة الموجَّهة إلى العميل، و__repr__ هي الصيغة القاطعة التي تريدها عند تتبع الأخطاء — وعليها أن تذكر اسم الصنف والقيم التي تعرّف الكائن.

class Order:
    def __init__(self, number, customer):
        self.number = number
        self.customer = customer
        self.items = []

    def __str__(self):
        return (f"Order #{self.number} — {self.customer}"
                f" — {len(self.items)} item(s)")

    def __repr__(self):
        return (f"Order(number={self.number!r},"
                f" customer={self.customer!r},"
                f" items={len(self.items)})")


a = Order(14, "Huda")
a.items.append(("mango juice", 10))
b = Order(15, "Yousef")

print(a)
print([a, b])

What !r does, and the fallback ruleما يفعله !r، وقاعدة التراجع

{self.customer!r} inserts the repr of the value, which is why the name shows as 'Huda' with quotes — so you can tell the string "14" from the number 14 while debugging. And the fallback goes one way only: if you define __repr__ but no __str__, then print(obj) uses __repr__. If you define only __str__, lists still print addresses. So when you write just one of the two, write __repr__.

تُدرج {self.customer!r} صيغة repr للقيمة، ولهذا يظهر الاسم 'Huda' بعلامتي تنصيص — فتميّز النص "14" من الرقم 14 أثناء تتبع الأخطاء. والتراجع يسير في اتجاه واحد فقط: فإن عرّفت __repr__ دون __str__، استخدم print(obj) الدالة __repr__. وإن عرّفت __str__ وحدها، ظلت القوائم تطبع العناوين. لذا إن كتبت واحدة منهما فقط، فاكتب __repr__.

While we are here: stop storing what you can computeوبما أننا هنا: توقف عن تخزين ما تستطيع حسابه

The receipt above showed the item count by computing len(self.items). The tempting alternative is to keep a total attribute and update it whenever something changes. It works exactly until the day somebody forgets.

أظهرت الفاتورة أعلاه عدد الأصناف بحساب len(self.items). والبديل المغري هو الاحتفاظ بخاصية total وتحديثها كلما تغيّر شيء. وهو يعمل بالضبط حتى اليوم الذي ينسى فيه أحدهم.

A stored total is a second source of truthالإجمالي المخزَّن مصدر حقيقة ثانٍ

The shop just gave away a falafel plate. items and total both claim to answer "what does this order cost?", and the moment they disagree, the object is lying with a straight face. Every single place that touches items must now also remember to touch total — and that is the Lesson 1 disease in a new costume.

المحل أهدى للتو طبق فلافل. فكل من items وtotal يدّعي الإجابة عن سؤال «كم يكلّف هذا الطلب؟»، وفي اللحظة التي يختلفان فيها يكذب الكائن بوجه جامد. وعلى كل موضع يلمس items أن يتذكر الآن لمس total أيضًا — وهذا هو داء الدرس 1 بزيّ جديد.

Step 3 — make the total a method, and let __str__ call itالخطوة 3 — اجعل الإجمالي دالة، ودع __str__ تستدعيها

If a value can be derived from other attributes, derive it on demand. add_item() changes the state; subtotal() and total() read it. Nothing can drift, because there is nothing to keep in step.

إذا كان بالإمكان استنتاج قيمة من خصائص أخرى، فاستنتجها عند الطلب. فـ add_item() تغيّر الحالة، وsubtotal() وtotal() تقرآنها. فلا شيء يمكن أن ينحرف، لأن لا شيء يحتاج إلى إبقائه متزامنًا.

class Order:
    vat_rate = 0.05

    def __init__(self, number, customer, discount=0):
        self.number = number
        self.customer = customer
        self.discount = discount
        self.items = []

    def add_item(self, name, price):
        self.items.append((name, price))

    def subtotal(self):
        return sum(price for name, price in self.items)

    def total(self):
        gross = self.subtotal() * (1 + self.vat_rate)
        return round(gross - self.discount, 2)

    def __str__(self):
        return (f"Order #{self.number} — {self.customer}"
                f" — {len(self.items)} item(s)"
                f" — {self.total()} ILS")

    def __repr__(self):
        return (f"Order(number={self.number!r},"
                f" items={len(self.items)},"
                f" total={self.total()})")

a.add_item("mango juice", 10)
print(a)

print(a)

Different domain, same principle. A water truck fills rooftop tanks. The driver needs one readable line per tank, the office needs an unambiguous one inside a list, and the fill percentage is computed rather than stored so it cannot lag behind the water.

مجال مختلف والمبدأ نفسه. شاحنة ماء تملأ خزانات الأسطح. فالسائق يحتاج سطرًا واحدًا مقروءًا لكل خزان، والمكتب يحتاج سطرًا قاطعًا داخل قائمة، ونسبة الامتلاء محسوبة لا مخزَّنة فلا يمكن أن تتأخر عن الماء.

class WaterTank:

        self.roof = roof
        self.capacity = capacity
        self.litres = 0

        self.litres += litres

        return round(self.litres / self.capacity * 100)

    def __str__(self):

        return f"WaterTank(roof={self.roof!r})"

You define __str__ only. What does print([order]) show?عرّفتَ __str__ فقط. فماذا تُظهر print([order])؟

Containers always format their contents with __repr__, so an undefined __repr__ leaves the memory address showing — exactly what Step 1's third output line did. The tempting wrong answer is the last one: the fallback exists but runs the other way round. __str__ falls back to __repr__, never the reverse, which is why defining __repr__ alone fixes both print(obj) and print([obj]).
الحاويات تنسّق محتواها دائمًا بـ __repr__، فبقاء __repr__ غير معرَّفة يُبقي عنوان الذاكرة ظاهرًا — وهذا بالضبط ما فعله السطر الثالث من ناتج الخطوة 1. والإجابة المغرية الخاطئة هي الأخيرة: فالتراجع موجود لكنه يسير في الاتجاه المعاكس. إذ ترجع __str__ إلى __repr__ ولا يحدث العكس أبدًا، ولهذا فإن تعريف __repr__ وحدها يصلح print(obj) وprint([obj]) معًا.

Second example — a training session at the centreمثال ثانٍ — حصة تدريبية في المركز

Different domain, all three ideas at once. A vocational training centre runs sessions. Every room holds 20 by default, so seats_default is a class attribute. __init__ gives seats and room defaults and creates the empty attendees list. __str__ prints the one line the coordinator pins on the door.

مجال مختلف، والأفكار الثلاث معًا. مركز تدريب مهني يُشغّل حصصًا تدريبية. وكل قاعة تتسع لعشرين افتراضيًا، فتكون seats_default خاصية صنف. ويمنح __init__ قيمًا افتراضية لـ seats وroom وينشئ قائمة attendees الفارغة. وتطبع __str__ السطر الواحد الذي يعلّقه المنسّق على الباب.

class ClassSession:
    seats_default = 20

    def __init__(self, topic, trainer, seats=None,
                 room="Lab 1"):
        self.topic = topic
        self.trainer = trainer
        if seats is None:
            seats = ClassSession.seats_default
        self.seats = seats
        self.room = room
        self.attendees = []

    def seats_left(self):
        return self.seats - len(self.attendees)

    def enrol(self, name):
        if self.seats_left() == 0:
            return f"{self.topic} is full"
        self.attendees.append(name)
        return f"{name} enrolled in {self.topic}"

    def __str__(self):
        return (f"{self.topic} / {self.trainer}"
                f" — {self.room} —"
                f" {self.seats_left()} seat(s) left")

                        seats=3, room="Lab 2")

print(excel_pm)

    print(excel_pm.enrol(name))

Three details worth copying. seats=None rather than seats=seats_default, because a parameter default cannot see names inside the class body being defined — the lookup happens in __init__'s body instead. room="Lab 1" is a safe default because a string is immutable and cannot be modified by one session on behalf of the others. Which value belongs on the class rather than on each object?أي قيمة تنتمي إلى الصنف لا إلى كل كائن؟

A class attribute is right for a fact that belongs to the kind, not to the individual: the centre's standard room size is one policy, so ClassSession.seats_default = 25 updates it everywhere. The tempting wrong answer is the first: a shared attendees list sounds efficient, but it is the mutable-default bug promoted to a feature — enrolling Huda in the Python session would also enrol her in Excel, exactly like the shared items=[] earlier. Anything an object modifies in place must be created per object, in __init__.
خاصية الصنف مناسبة لحقيقة تنتمي إلى النوع لا إلى الفرد: فحجم القاعة المعياري في المركز سياسة واحدة، لذا يحدّثها ClassSession.seats_default = 25 في كل مكان. والإجابة المغرية الخاطئة هي الأولى: فقائمة attendees المشتركة تبدو موفِّرة، لكنها خلل القيمة الافتراضية القابلة للتغيير وقد رُقِّي إلى ميزة — فتسجيل هدى في حصة Python سيسجّلها في Excel أيضًا، تمامًا كما حدث مع items=[] المشتركة سابقًا. فكل ما يعدّله الكائن في مكانه يجب أن يُنشأ لكل كائن داخل __init__.

  • When objects are built by hand in several places, "what does a valid object contain?" has several answers, and they disagree. __init__ makes it one place with one answer.عندما تُبنى الكائنات يدويًا في مواضع عدة، يصبح لسؤال «ما الذي يحتويه الكائن السليم؟» إجابات عدة تتناقض. و__init__ يجعله موضعًا واحدًا بإجابة واحدة.
  • __init__ should set every attribute the object will ever have: the passed-in ones, the defaulted ones, and the empty or derived ones such as self.items = [] and self.created_at.على __init__ ضبط كل خاصية سيملكها الكائن يومًا: المُمرَّرة، وذات القيمة الافتراضية، والفارغة أو المشتقة مثل self.items = [] وself.created_at.
  • Adding a field then becomes a one-line change in one place, instead of a hunt through every construction site in which one is always missed.وتصبح إضافة حقل حينئذ تعديلًا في سطر واحد في مكان واحد، بدلًا من مطاردة في كل مواضع البناء يُنسى فيها واحد دائمًا.
  • Never write a list, dict or set as a parameter default. Defaults are evaluated once at definition time, so every object shares that one value. Write None and build the real value in the body.لا تكتب قائمة أو قاموسًا أو مجموعة كقيمة افتراضية لمعامل أبدًا. فالقيم الافتراضية تُقيَّم مرة واحدة عند التعريف، فيتشارك كل الكائنات تلك القيمة الواحدة. اكتب None وابنِ القيمة الحقيقية في الجسم.
  • A fact that belongs to the whole kind — a VAT rate, a shop name, a default room size — belongs on the class, written once in the class body, not copied into every object.الحقيقة التي تنتمي إلى النوع كله — نسبة ضريبة، اسم محل، سعة قاعة افتراضية — تنتمي إلى الصنف، تُكتب مرة واحدة في جسم الصنف، لا تُنسخ في كل كائن.
  • Reading obj.x checks the object first, then the class. Writing obj.x = v always creates an instance attribute that shadows the class one for that object forever; only Class.x = v changes the shared value.قراءة obj.x تفحص الكائن أولًا ثم الصنف. والكتابة obj.x = v تنشئ دائمًا خاصية كائن تحجب خاصية الصنف عن ذلك الكائن إلى الأبد؛ وحدها Class.x = v تغيّر القيمة المشتركة.
  • __str__ is the human line (print(obj), f-strings); __repr__ is the debugging line and the one containers use. The fallback runs one way: define only __repr__ and both work.__str__ هي السطر الموجَّه إلى الإنسان (print(obj) وf-strings)؛ و__repr__ هي سطر تتبع الأخطاء وهي ما تستخدمه الحاويات. والتراجع يسير في اتجاه واحد: عرّف __repr__ وحدها فتعمل الاثنتان.
  • Giving the object its own __str__ replaces every scattered print_order(...) helper, so one receipt is printed the same way from everywhere in the program.منح الكائن دالة __str__ خاصة به يُغني عن كل دالة print_order(...) مبعثرة، فتُطبع فاتورة واحدة بالطريقة نفسها من كل موضع في البرنامج.
  • Compute from state instead of storing it. A stored total is a second source of truth that drifts the first time someone adds an item and forgets to update it; total() cannot be out of date.احسب من الحالة بدلًا من تخزينها. فـ total المخزَّن مصدر حقيقة ثانٍ ينحرف في أول مرة يضيف فيها أحدهم صنفًا وينسى تحديثه؛ أما total() فلا يمكن أن تتقادم.
