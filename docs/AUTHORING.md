# Authoring a Chapter

How the repository is put together, and the exact steps to add Chapter 2.
The rules a chapter must satisfy are in [SPEC.md](SPEC.md); this is the
mechanics.

## Layout

The site is many pages sharing one set of engines. The pages are generated;
everything under `assets/` is hand-written and served as it is.

```
index.html                   course home            \
chapters/chapter-N.html      chapter home            |  generated by build.py
lessons/chapter-N-lesson-M.html                      |  from src/content/ --
tests/chapter-N-test-M.html  one per lesson test     |  never edit by hand
exams/chapter-N-exam-a|b.html                        |
labs/chapter-N-lab.html      the execution lab       |
appendices/appendix-aN.html  the self-study material/

assets/
|-- css/tokens.css           colours, radii, fonts; light and dark
|-- css/base.css             elements: typography, code, tables, print
```

### Where a page comes from

`src/content/*.html` holds `<section class="page" id="...">` blocks -- one per
page -- and `assets/js/course.js` says where each id is written to and what it
is called. `build.py` puts the two together: it wraps each section in the
shared shell, works out how many `../` that page needs, decides which
stylesheets and scripts it loads, and rewrites the author's `href="#lesson-03"`
into a real path to the file that id ended up in.

That last part is what `assets/js/anchors.js` is for: it maps every id in the
content to the page holding it, so a topic chip under a question can still link
to the paragraph that teaches the idea, now that the paragraph is elsewhere.

```bash
python3 build.py                 # write the pages and anchors.js
python3 build.py --check         # are the committed pages current?
python3 scripts/build-sw.py      # rewrite sw.js after adding/removing a file
```

`build.py --check` exits non-zero if any page on disk differs from what the
sources would produce. Run it before committing; `tools/verify_chapter.py`
runs it for you.

## Data formats

### A question

```js
{
  id: "t3q7",              // unique across the whole chapter
  type: "output",          // one of the eleven types in SPEC §3.3
  level: "medium",         // easy | medium | hard
  topics: ["property", "setter"],   // keys from data/topics.js
  q: { en: "...", ar: "..." },      // the stem; HTML allowed
  code: "class X:\n    ...",        // optional; raw Python, escaped at render
  codeA / codeB: "...",             // for type "compare"

  // then whichever answer shape the type needs:
  options: [{en, ar}] | [{code}],  answer: 0 | [0, 2],
  truth: true,                                   // tf
  blanks: [{ accept: ["..."], label: {en, ar}, wide: true, lines: 3, hint: {} }],
  items:  [{en, ar}], answer: [0, 1, 2],         // order
  pairs:  [{ l: {}, r: {} }],                    // match (answer is identity)
  answer: 6,                                     // error: the 1-based line

  explain:  { en: "...", ar: "..." },            // required
  solution: { code: "...", out: "...", en, ar }  // optional
}
```

Notes that save time:

- `answer` for `match` is implicit: `pairs[i].l` pairs with `pairs[i].r`.
  Options and right-hand columns are shuffled per question, deterministically,
  so the display is mixed but stable across re-renders and language flips.
- `output` blanks compare line by line with surrounding whitespace stripped,
  so the student does not have to reproduce column padding. Everything else
  compares exactly after collapsing internal runs of spaces.
- Give `accept` every spelling you will take: `["250.0", "250", "250.00"]`.
- A type can be authored two ways and the engine picks the widget from the
  data: an `output` with `options` becomes multiple choice, an `output` with
  `blanks` becomes typed. Same for `complete`, `trace` and `error`.

### A trace

```js
"t-key": {
  id, title: {en, ar}, lede: {en, ar},
  code: "line\nline\n...",
  steps: [{ line: 7,                     // 1-based, about to take effect
            vars: { "a": "Book(...)" },  // the FULL picture, not a delta
            out: "everything printed so far",
            scope: {en, ar},             // whose self you are inside
            note:  {en, ar} }]
}
```

The widget diffs consecutive `vars` to decide what to flash, so each step
repeats the unchanged variables.

### A topic

```js
"property": { href: "l3-s3", en: "@property", ar: "@property" }
```

`href` is a heading id. `tools/add_anchor_ids.py` gives every `h2`/`h3` in the
content a stable id (`l3-h1` for the first `h2` of lesson 3, `l3-s4` for its
fourth `h3`) and is idempotent — run it again after adding headings.

## Steps to add the next chapter

Chapters 1 to 4 are written; the lectures each remaining chapter is allowed
are in [SPEC.md](SPEC.md) §0 and the lecture plan is in
[SYLLABUS.md](SYLLABUS.md).

1. Write `src/content/chapter-NN.html`: the chapter home section first, then
   one section per lesson. Page ids are unique across the whole course and
   course-wide, not per chapter — `chapter-3`, `lesson-12`, `test-12`,
   `chapter-03-test-a`. Follow the prose structure of the chapters already
   written (problem -> diagnosis -> conversion -> second example -> exercises
   -> key takeaways), and put an exercise or an inline check every 5 to 10
   minutes of reading rather than collecting them at the end.
2. `python3 tools/add_anchor_ids.py` to give the new headings ids. Extend the
   script's `PATHS` or run it per content file.
3. Add topic entries to `assets/data/topics.js` pointing at those ids.
4. Write the test sections in `src/content/chapter-NN-tests.html` and the
   banks in `assets/data/questions-*.js`.
5. Author traces in `assets/data/traces-chapter-NN.js` and mount each one in
   the lesson that needs it with `<div data-trace-id="t-..."></div>`.
   `build.py` sees the mount and gives that page the lab's stylesheet, the
   chapter's trace file and `trace.js`; there is nothing to register.
6. Add the chapter to `CHAPTERS` in `assets/js/course.js` — its number, slug,
   title, blurb, stats, and every page in reading order with the `href` it is
   written to, each lesson carrying its course-wide `n`. Add the two content
   files to `CONTENT` in `build.py`, and map each new bank to its question
   file in `BANK_FILE`. Drop the chapter from `PLANNED` in `course.js` so the
   home page stops calling it unwritten.
7. Add a chapter card to `src/content/home.html`, with a
   `data-chapter-progress` span. Without it the chapter is reachable only by
   typing its URL: the drawer only ever lists the open chapter.
8. `python3 build.py && python3 scripts/build-sw.py`, then run the checks
   below.

The registry drives the drawer, the breadcrumbs, the pager, the home page,
the precache list, the build and the end-to-end suite. Nothing else needs
telling that a chapter exists.

### Two rules that are easy to break quietly

1. **Every data file extends its registry; none replaces it.** Start each one
   with `window.OOPBanks = window.OOPBanks || {}` (or `OOPTraces`, or
   `OOPTopics`) and then assign into it. `verify_chapter.py` loads every file
   in `assets/data` in sorted order, so a bare `window.OOPTraces = {...}` in
   `traces.js` silently drops every chapter whose file sorts before it.
2. **Never refer to an option by its position.** `assess.js` shuffles the
   options of every `mcq`, `multi` and `compare` question deterministically
   per question id, so "the second option" in an explanation points at
   whatever that student happens to be shown — and the explanation is what
   they read *after* getting it wrong. Name the option by its content instead
   ("the answer that calls scaling a distortion"). The same applies to
   `match` pairs, whose right-hand column is shuffled; `order` steps are
   safe, because the explanation discusses the answer sequence.

### Appendices

An appendix belongs to no chapter: it is self-study, it is never examined,
and it exists so a lesson can state a result and point at where it is
explained instead of deriving it in a lecture.

They live in one group in the registry, `APPENDICES`, shaped exactly like a
chapter and numbered 0 so that the drawer, the breadcrumbs, the pager and the
build all read them with the code that already reads chapters. The 0 is never
shown — the group has a title of its own. To add one: write
`src/content/appendix-aN.html`, add it to `CONTENT`, add its bank to
`BANK_FILE`, add a page entry to `APPENDICES` with `kind: "appendix"`, and
add a card to the appendix grid in `src/content/home.html`.

A new top-level directory of pages also has to be added to `DIRS` in
`scripts/build-sw.py` and to `PAGE_DIRS` in `tools/verify_chapter.py`, or the
pages will not be precached and the verifier will not see them.

## Checks before committing

```bash
python3 build.py                     # rebuild the pages
python3 scripts/build-sw.py          # rebuild the precache list
python3 tools/verify_chapter.py      # structure, links, assets, metadata
npx playwright test                  # drive the real thing in a real browser
```

`tools/verify_chapter.py` is the first gate. It fails on a link to a page that
does not exist or to an anchor that page does not have, a stylesheet or script
a page loads but does not ship, a page that loads an engine it never uses, a
stale build, a precache list out of step with the site, a question with no
explanation or no topics, an unknown topic key, a duplicate question id, a
trace step pointing outside its code, a missing question type, or a bilingual
string present in one language only.

`npx playwright test` is the second gate, and the one that catches what static
checking cannot: it walks the pager through the whole chapter, answers a real
question of every widget kind and checks the grade, steps the execution lab
against its authored trace, flips the language and the theme and then
navigates to prove both survived, cuts the network and loads a page that was
never visited online, and measures every page at 320, 390, 768 and 1280px in
both reading directions for sideways overflow. `npm run serve` starts the
authoring server separately if you want to click around yourself.

Verify every code output by running it before you paste it into a question.
Keep the snippets in a scratch file and run them with `python3 -I`.

## Conventions

- Vanilla ES5-compatible JavaScript: `var`, no arrow functions, no `const`.
  The engine is read by a student eventually; keep it plain.
- Bilingual strings are always `{ en, ar }`, rendered as
  `<span class="en">…</span><span class="ar">…</span>` and switched by CSS.
- Python in `code` fields is raw; the engine escapes it. Write `>` not `&gt;`.
- `localStorage` keys are namespaced `oop.*`. Answers are stored per bank so a
  student keeps their progress; `Start over` clears one test's bank only.
- Never edit a built page by hand -- `index.html`, `chapters/`, `lessons/`,
  `tests/`, `exams/`, `labs/` -- nor `assets/js/anchors.js` or `sw.js`.
  All of them are generated; edit `src/content/` or `assets/js/course.js`
  and rebuild.
