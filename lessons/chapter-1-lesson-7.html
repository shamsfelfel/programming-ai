Lesson 7

Capstone: Two Styles, One Programالمشروع الختامي: أسلوبان لبرنامج واحد

There is no new concept in this lesson. One real program — a phone repair shop's ticket desk — is written twice, once with dicts and functions and once with classes, and the two files print byte-for-byte identical output; by the end you will be able to point at any line of the object-oriented file and name the lesson that earned it, and to say out loud which of the two files you would rather be handed next Tuesday when the shop changes its mind.

لا مفهوم جديد في هذا الدرس. فبرنامج واحد حقيقي — مكتب تذاكر في محل تصليح هواتف — مكتوب مرتين، مرة بالقواميس والدوال ومرة بالأصناف، والملفان يطبعان ناتجًا مطابقًا حرفًا بحرف؛ وبنهايته ستكون قادرًا على أن تشير إلى أي سطر في الملف الكائني وتسمّي الدرس الذي كسبه، وعلى أن تقول بصوت مسموع أيّ الملفين تفضّل أن يُسلَّم إليك الثلاثاء القادم حين يغيّر المحل رأيه.

What this lesson isما هذا الدرس

Six lessons each introduced one idea against one small example. A real program is not six small examples; it is one body of code in which encapsulation, polymorphism and composition have to share a file and get along. This lesson replays the whole course on one such program, so that the principles stop being six separate techniques and become one way of reading code.

قدّم كلٌّ من الدروس الستة فكرةً واحدة في مقابل مثال صغير واحد. والبرنامج الحقيقي ليس ستة أمثلة صغيرة؛ إنه جسد كود واحد يضطر فيه التغليف وتعدد الأشكال والتركيب إلى مشاركة ملف والتوافق فيه. فيعيد هذا الدرس تمثيل المنهج كله على برنامج من هذا القبيل، لتكفّ المبادئ عن أن تكون ستّ تقنيات منفصلة وتصبح طريقةً واحدة في قراءة الكود.

Both versions are good code. The structured one is not a strawman written badly on purpose so that classes can look clever beside it — it is the version a careful programmer writes without classes, and you should read it as something you would be content to have written. The question this lesson asks is not "which is correct" but "which one costs less when the requirement changes", and the answer turns out to depend on which requirement changes.

النسختان كودٌ جيّد. فالنسخة البنيوية ليست خصمًا من قشّ كُتب سيّئًا بقصد أن تبدو الأصناف بارعة بجانبه — بل هي النسخة التي يكتبها مبرمج متيقّظ بلا أصناف، وينبغي أن تقرأها كشيء يرضيك أن تكون كتبته. والسؤال الذي يطرحه هذا الدرس ليس «أيّهما صحيح» بل «أيّهما أقلّ كلفةً حين يتغيّر المطلوب»، ويتبيّن أن الجواب يعتمد على أيّ مطلوب يتغيّر.

Version 1 — the structured programالنسخة 1 — البرنامج البنيوي

The problemالمشكلة

The shop has one laptop behind the counter and one program on it, written by a cousin who studied programming for two terms. It works. It has worked for a year. In that year the shop started doing water damage, which it did not do before; it hired a second technician; it added the "waiting for part" state to a whiteboard because the program had no room for it; and the owner is now talking about a second counter in Rafah.

للمحل حاسوب محمول واحد وراء المنضدة وبرنامج واحد عليه، كتبه قريبٌ درس البرمجة فصلين. وهو يعمل. وقد عمل عامًا. وفي ذلك العام بدأ المحل يعمل في أضرار الماء ولم يكن يعملها قبل؛ ووظّف فنيًّا ثانيًا؛ وأضاف حالة «في انتظار قطعة» إلى لوح أبيض لأنه لا موضع لها في البرنامج؛ ويتحدّث المالك الآن عن منضدة ثانية في رفح.

None of that is a bug report. Every one of those is a change, and the only question a design can be judged by is what each one costs to make. So read the structured program below not as a thing that might be wrong, but as a thing that will be edited — by you, on a Tuesday, in a hurry — and keep a running count of how many places each request would touch.

ولا شيء من ذلك تقرير عِلّة. فكل واحد من تلك تغيير، والسؤال الوحيد الذي يُحكَم به على تصميم هو ما تكلّفه كل واحدة منها. فاقرأ البرنامج البنيوي أدناه لا شيئًا قد يكون خاطئًا، بل شيئًا سيُعدَّل — بيدك، في يوم ثلاثاء، على عجل — وأبقِ حسابًا جاريًا لعدد المواضع التي سيمسّها كل طلب.

File: repair_shop_structured.py, 177 lines. Dictionaries for the data, functions for the verbs, one module-level constant block at the top. This is the shape most working Python in the world has.

الملف: repair_shop_structured.py، 177 سطرًا. قواميس للبيانات، ودوال للأفعال، وكتلة ثوابت واحدة على مستوى الوحدة في الأعلى. وهذه هي الصورة التي عليها أكثر كود بايثون العامل في العالم.

Part 1 — the data shapeالجزء 1 — شكل البيانات

A ticket is a dict. There is no class to enforce which keys exist, so one factory function is written to build them all — this is already a good decision, and the only reason the nine keys stay consistent across six tickets.

التذكرة قاموس. ولا صنف يفرض أي المفاتيح موجودة، فتُكتب دالة مصنع واحدة لبنائها كلها — وهذا قرار جيّد أصلًا، وهو السبب الوحيد في بقاء المفاتيح التسعة متّسقة على ستّ تذاكر.

"""Phone repair shop ticket desk -- structured version.

Same behaviour as repair_shop_oop.py: lists, dicts and functions
instead of classes. No input() anywhere; main() runs a fixed
scenario so the two files can be diffed line for line.
"""

# ---- shop constants -------------------------------------------

DIAG_FEE = 20.0             # charged on every ticket
URGENT_RATE = 0.25          # surcharge on an urgent job
BATTERY_FITTING = 10.0      # calibration after a new battery
WATER_INSPECTION = 35.0     # cost of opening a wet phone
CORROSION_FACTOR = 1.5      # corroded boards need more parts

STATUS_FLOW = ["received", "in progress", "ready", "collected"]


# ---- the data shape -------------------------------------------

def make_ticket(tid, customer, device, kind, priority, parts,
                technician, corrosion=False):
    """Build one repair ticket as a plain dictionary."""
    return {
        "id": tid,
        "customer": customer,
        "device": device,
        "kind": kind,              # screen / battery / water
        "priority": priority,      # normal / urgent
        "parts": parts,            # parts estimate in ILS
        "technician": technician,
        "corrosion": corrosion,    # only read for water jobs
        "status": "received",
    }

Notice corrosion. It is meaningful only for a water job, and it sits on every ticket anyway, because a dict has one shape for all its instances. A screen replacement carries a corrosion flag it will never consult. That is not a bug; it is the first small tax of one shape fitting three kinds of thing.

لاحظ corrosion. فهي ذات معنى لعمل الماء وحده، وهي قائمة على كل تذكرة رغم ذلك، لأن للقاموس شكلًا واحدًا لكل حالاته. فاستبدال الشاشة يحمل راية تآكل لن يراجعها أبدًا. وذلك ليس عِلّة؛ بل هو أول ضريبة صغيرة لشكلٍ واحد يفي بثلاثة أنواع من الأشياء.

Part 2 — pricing: one function, three branchesالجزء 2 — التسعير: دالة واحدة وثلاثة فروع

The three pricing rules go into one if/elif chain, and the urgent surcharge goes into a second function that wraps it. That split is well done: the surcharge is written once and applies to all three kinds, so nobody has to remember to add 25% in three places.

تذهب قواعد التسعير الثلاث إلى سلسلة if/elif واحدة، وتذهب زيادة الاستعجال إلى دالة ثانية تلفّها. وذلك الفصل مُحسَن: فالزيادة مكتوبة مرة واحدة وتسري على الأنواع الثلاثة، فلا يضطر أحد إلى تذكّر إضافة 25% في ثلاثة مواضع.

# ---- pricing --------------------------------------------------

def job_subtotal(ticket):
    """Diagnosis fee plus parts, priced per kind of job."""
    kind = ticket["kind"]
    parts = ticket["parts"]
    if kind == "screen":
        return DIAG_FEE + parts
    elif kind == "battery":
        return DIAG_FEE + parts + BATTERY_FITTING
    elif kind == "water":
        if ticket["corrosion"]:
            parts = parts * CORROSION_FACTOR
        return DIAG_FEE + WATER_INSPECTION + parts
    else:
        raise ValueError(f"unknown job kind: {kind}")


def quote(ticket):
    """The customer's price: subtotal plus urgent surcharge."""
    total = job_subtotal(ticket)
    if ticket["priority"] == "urgent":
        total = total * (1 + URGENT_RATE)
    return total

And credit where it is due: the else raises. Lesson 6's clinic had a silent else that priced an unknown type at the full fee and lost money quietly for a year. This one refuses to guess. A reviewer should ask for exactly this, and here it already is.

والفضل لذي فضل: فرع else يرفع خطأ. فكان لعيادة الدرس 6 فرع else صامت يسعّر نوعًا مجهولًا بالأجر الكامل فيخسر المال في صمت عامًا كاملًا. وهذا يرفض التخمين. وينبغي للمراجع أن يطلب هذا بالضبط، وهو ها هنا أصلًا.

Part 3 — the status flowالجزء 3 — مسار الحالات

The legal order lives in one list, STATUS_FLOW, and the rule is derived from it rather than written out as six comparisons. next_status answers "where may this ticket go", and step is the single function the rest of the program is supposed to call.

يقيم الترتيب القانوني في قائمة واحدة، STATUS_FLOW، وتُستنبط القاعدة منها لا تُكتب ستّ مقارنات. فـ next_status تجيب «إلى أين يجوز لهذه التذكرة أن تمضي»، وstep هي الدالة الوحيدة التي يُفترض ببقية البرنامج أن تستدعيها.

# ---- status flow ----------------------------------------------

def next_status(status):
    """The only status a ticket is allowed to move to."""
    i = STATUS_FLOW.index(status)
    if i + 1 < len(STATUS_FLOW):
        return STATUS_FLOW[i + 1]
    return None


def step(ticket, new_status):
    """Move a ticket one step, or refuse and say why."""
    old = ticket["status"]
    if new_status != next_status(old):
        print(f"  {ticket['id']} -- rejected: cannot go"
              f" from {old} to {new_status}")
        return False
    ticket["status"] = new_status
    print(f"  {ticket['id']} -> {new_status}")
    return True

This is the one place the structured version is making a promise it cannot keep, and it is worth naming now rather than at the end. The rule is correct. The rule is also optional: ticket["status"] = "collected" works from anywhere in the program, in any file that imports this one, and it bypasses step entirely. The guard is a convention — a door with a sign on it, in a wall with no bricks.

هذا هو الموضع الوحيد الذي تَعِد فيه النسخة البنيوية وعدًا لا تستطيع الوفاء به، ويجدر تسميته الآن لا في النهاية. فالقاعدة صحيحة. والقاعدة اختيارية أيضًا: فـ ticket["status"] = "collected" تعمل من أي موضع في البرنامج، وفي أي ملف يستورد هذا الملف، وتتجاوز step تجاوزًا تامًّا. فالحارس عُرْف — بابٌ عليه لافتة، في جدار بلا طوب.

Part 4 — intake and the reportالجزء 4 — الاستلام والتقرير

Four small functions, each one doing one countable thing, and a fifth that prints. Every one of them takes tickets as its first parameter — remember that detail, it comes back in the comparison.

أربع دوال صغيرة، تؤدي كل واحدة شيئًا واحدًا قابلًا للعدّ، وخامسةٌ تطبع. وتأخذ كل واحدة منها tickets معاملها الأول — فتذكّر تلك التفصيلة، فهي تعود في المقارنة.

# ---- intake and report ----------------------------------------

def print_intake(tickets):
    """One line per ticket with its quoted price."""
    print("intake")
    for t in tickets:
        print(f"  {t['id']} {t['customer']:16}"
              f"{t['device']:14}{t['kind']:8}"
              f"{t['priority']:7}{quote(t):8.2f}")


def count_status(tickets, status):
    """How many tickets sit on this status right now."""
    return sum(1 for t in tickets if t["status"] == status)


def income(tickets):
    """Money actually taken: collected tickets only."""
    return sum(quote(t) for t in tickets
               if t["status"] == "collected")


def workload(tickets):
    """Technician name -> number of tickets assigned."""
    load = {}
    for t in tickets:
        name = t["technician"]
        load[name] = load.get(name, 0) + 1
    return load


def print_report(tickets):
    """Tickets per status, income, busiest technician."""
    print("daily report")
    print("  tickets per status")
    for status in STATUS_FLOW:
        print(f"    {status:14}{count_status(tickets, status):2}")
    print(f"  income collected   {income(tickets):8.2f} ILS")
    load = workload(tickets)
    busiest = max(load, key=lambda name: load[name])
    print(f"  busiest technician {busiest}"
          f" ({load[busiest]} tickets)")

This part is the structured version at its best, and it needs no apology at all. income is four lines and obviously right. workload is a dict accumulator any reader can check in ten seconds. print_report loops over STATUS_FLOW instead of printing four hard-coded labels, which means adding a status to the list will extend the report with no edit here. An object-oriented rewrite will not make any of these shorter or clearer — it will only move them.

هذا الجزء هو النسخة البنيوية في أحسن حالها، ولا يحتاج اعتذارًا إطلاقًا. فـ income أربعة أسطر وصحيحة بوضوح. وworkload مجمّع قاموس يستطيع أي قارئ التحقّق منه في عشر ثوانٍ. وprint_report تدور على STATUS_FLOW لا تطبع أربع لافتات مثبتة في الكود، ومعنى ذلك أن إضافة حالة إلى القائمة ستمدّ التقرير بلا تعديل هنا. ولن تجعل إعادةُ كتابةٍ كائنيةٌ أيًّا من هذه أقصر ولا أوضح — بل ستنقلها فحسب.

Part 5 — the scripted dayالجزء 5 — اليوم المكتوب

Six tickets, a work log, a report. The last two step calls are the interesting ones: T-103 goes to in progress, then the customer turns up asking for the phone.

ستّ تذاكر، وسجلّ عمل، وتقرير. واستدعاءا step الأخيران هما المثيران: فـ T-103 تمضي إلى in progress، ثم يحضر العميل طالبًا الهاتف.

# ---- the scripted day -----------------------------------------

def main():
    title = "Gaza Phone Clinic -- repair desk"
    print(title)
    print("-" * len(title))
    print()

    tickets = [
        make_ticket("T-101", "Huda Nassar", "iPhone 11",
                    "screen", "normal", 180.0,
                    "Samir Qeshta"),
        make_ticket("T-102", "Rami Hania", "Galaxy A12",
                    "battery", "urgent", 70.0,
                    "Lina Barhoum"),
        make_ticket("T-103", "Mona Abu Shaar", "Redmi Note 9",
                    "water", "normal", 90.0,
                    "Samir Qeshta", corrosion=True),
        make_ticket("T-104", "Kareem Zourob", "iPhone XR",
                    "screen", "urgent", 220.0,
                    "Samir Qeshta"),
        make_ticket("T-105", "Dalia Khoudary", "Nokia G21",
                    "battery", "normal", 55.0,
                    "Lina Barhoum"),
        make_ticket("T-106", "Basel Madhoun", "Galaxy S10",
                    "water", "normal", 120.0,
                    "Samir Qeshta"),
    ]
    print_intake(tickets)
    print()

    by_id = {t["id"]: t for t in tickets}
    print("work log")
    for tid in ("T-101", "T-102", "T-105"):
        step(by_id[tid], "in progress")
        step(by_id[tid], "ready")
        step(by_id[tid], "collected")
    step(by_id["T-104"], "in progress")
    step(by_id["T-104"], "ready")
    step(by_id["T-103"], "in progress")
    # the customer arrives before the phone is ready
    step(by_id["T-103"], "collected")
    print()

    print_report(tickets)


if __name__ == "__main__":
    main()

What this version does wellما تُحسنه هذه النسخة

Say it plainly, because the next section will be flattering to the other file. Every function here is short, named for what it returns, and testable by calling it with a list of dicts — no object to construct first. The whole program can be read top to bottom in one pass with no jumping. A new developer needs to know zero vocabulary beyond dicts, lists and functions to change the battery fitting fee. The business rules are not hidden anywhere: three pricing rules in one chain, one status rule in STATUS_FLOW. For a program of this size, handed to a competent programmer who will read it once and edit one number, this file is arguably the better deliverable of the two.

Part 1 — the job types (Lessons 4, 5, 6)الجزء 1 — أنواع العمل (الدروس 4 و5 و6)

The if/elif chain from job_subtotal becomes three classes with one method each. Job(ABC) with @abstractmethod is Lesson 4's abstraction: the base class names the question every job must answer and refuses to be instantiated itself. The three subtotal bodies are Lesson 6's polymorphism — same name, three implementations, and the caller never asks which. """Repair shop desk, OOP. Same output as the structured file."""

from abc import ABC, abstractmethod

# ---- shop constants -------------------------------------------

DIAG_FEE = 20.0             # charged on every ticket
URGENT_RATE = 0.25          # surcharge on an urgent job
BATTERY_FITTING = 10.0      # calibration after a new battery
WATER_INSPECTION = 35.0     # cost of opening a wet phone
CORROSION_FACTOR = 1.5      # corroded boards need more parts

STATUS_FLOW = ["received", "in progress", "ready", "collected"]

# ---- the job types: one price rule each -----------------------

class Job(ABC):
    def __init__(self, parts):
        self.parts = parts

    @abstractmethod
    def subtotal(self):
        """Diagnosis fee plus whatever this job needs."""


class ScreenJob(Job):
    kind = "screen"

    def subtotal(self):
        return DIAG_FEE + self.parts


class BatteryJob(Job):
    kind = "battery"

    def subtotal(self):
        return DIAG_FEE + self.parts + BATTERY_FITTING


class WaterJob(Job):
    kind = "water"

    def __init__(self, parts, corrosion=False):
        super().__init__(parts)
        self.corrosion = corrosion

    def subtotal(self):
        parts = self.parts
        if self.corrosion:
            parts = parts * CORROSION_FACTOR
        return DIAG_FEE + WATER_INSPECTION + parts

Three things the structured version could not do are now true. corrosion exists only on WaterJob, so a ScreenJob has no corrosion flag to be confused by — the data shape finally matches reality. kind is a class attribute, Lesson 2: one string per type, stored once for the whole class and not copied into every ticket. And the else: raise ValueError branch has nowhere to live, because you can no longer be holding a job of an unknown kind: an unknown kind is an unwritten class, and an unwritten class cannot be instantiated.

ثلاثة أمور لم تستطعها النسخة البنيوية صارت صحيحة الآن. فـ corrosion موجودة على WaterJob وحده، فلا راية تآكل لـ ScreenJob يلتبس بها — فشكل البيانات صار مطابقًا للواقع أخيرًا. وkind خاصية صنف، الدرس 2: نصّ واحد لكل نوع، يُخزَّن مرة واحدة للصنف كله ولا يُنسَخ في كل تذكرة. وفرع else: raise ValueError لا موضع له ليقيم فيه، لأنك لم تعد تستطيع أن تحمل عملًا من نوع مجهول: فالنوع المجهول صنف غير مكتوب، والصنف غير المكتوب لا يُنشأ.

Lesson 4. Why is Job an ABC with an abstract subtotal, rather than a plain class whose subtotal returns DIAG_FEE?الدرس 4. لِمَ كان Job صنف ABC له subtotal مجرّدة، لا صنفًا صريحًا تعيد subtotal فيه DIAG_FEE؟

A default that is wrong but plausible is the most expensive kind of bug, because nothing ever complains: a new job type with no subtotal would quote every repair at 20.00 ILS and the shop would find out from its bank. @abstractmethod converts that into TypeError: Can't instantiate abstract class ... without an implementation for abstract method 'subtotal', on your machine, before a single ticket exists. Note what the base class still does: it holds __init__ and self.parts, which is Lesson 5's inheritance — an ABC can demand one method and donate another in the same breath. The third and fourth options are both invented; super() and shared attributes work on any class.
الافتراض الخاطئ المعقول أغلى أنواع العلل، لأن لا شيء يشكو قط: فلكان نوع عمل جديد بلا subtotal يسعّر كل إصلاح 20.00 شيكلًا وكان المحل سيعلم من مصرفه. وتحوّل @abstractmethod ذلك إلى TypeError: Can't instantiate abstract class ... without an implementation for abstract method 'subtotal'، على حاسوبك، قبل وجود تذكرة واحدة. ولاحظ ما يبقى صنف الأساس يفعله: فهو يحمل __init__ وself.parts، وذلك وراثة الدرس 5 — فيستطيع ABC أن يطالب بدالة ويتبرّع بأخرى في نَفَس واحد. والخياران الثالث والرابع مُختلَقان؛ فـ super() والخصائص المشتركة تعمل على أي صنف.

Lesson 6. Ticket.quote calls self.job.subtotal() and never mentions ScreenJob, BatteryJob or WaterJob. What does that one line buy?الدرس 6. تستدعي Ticket.quote الدالةَ self.job.subtotal() ولا تذكر ScreenJob ولا BatteryJob ولا WaterJob قط. فماذا يشتري ذلك السطر الواحد؟

Polymorphism is measured at the call site, by what the caller does not have to know: Ticket was written before WarrantyRepair existed and prices it correctly anyway, which is the whole of Exercise 7.2. The fourth option is the one that deserves a real answer rather than a dismissal, because it is half right — job_subtotal(ticket) is indeed one call written once, and the two lines look equally short. The difference is behind the call: that function body contains the list of kinds, so a new kind means editing it, while self.job.subtotal() contains no list at all. One call site, two very different blast radii. The first option is the usual false economy — the string test it saves is nanoseconds and was never the argument. The third invents a guarantee nothing can make: an ABC promises a method exists, never that its arithmetic is right, and a subtotal that returns self.parts * 100 satisfies it completely.
يُقاس تعدد الأشكال في موضع الاستدعاء بما لا يلزم المستدعي أن يعرفه: فقد كُتب Ticket قبل وجود WarrantyRepair ويسعّره تسعيرًا صحيحًا رغم ذلك، وذلك هو تمرين 7.2 كله. والخيار الرابع هو الذي يستحقّ جوابًا حقيقيًّا لا نفضًا، لأنه نصف صحيح — فـ job_subtotal(ticket) استدعاء واحد مكتوب مرة واحدة فعلًا، والسطران يبدوان قصيرين سواءً بسواء. والفرق خلف الاستدعاء: فجسد تلك الدالة فيه قائمةُ الأنواع، فيعني النوع الجديد تعديلَها، أما self.job.subtotal() فلا قائمة فيها إطلاقًا. موضع استدعاء واحد، ونطاقا انفجار مختلفان جدًّا. والخيار الأول هو الاقتصاد الكاذب المعتاد — ففحص النصّ الذي يوفّره نانوثوانٍ ولم يكن حجّةً قط. والثالث يختلق ضمانًا لا يستطيعه شيء: فـ ABC يعد بأن الدالة موجودة، لا بأن حسابها صحيح قط، وsubtotal التي تعيد self.parts * 100 تُرضيه إرضاءً تامًّا.
Part 2 — the ticket, with a guarded status (Lessons 2, 3, 5, 6)الجزء 2 — التذكرة بحالة محروسة (الدروس 2 و3 و5 و6)

self.job = job is Lesson 5's composition: a ticket has a job, it is not a kind of job. That one line is why a ticket's own class knows nothing about screens or water. _status with a read-only @property and one advance() method is Lesson 3's encapsulation, and this is the part that actually changes what the program is capable of being broken by. quote is a @property too, so it reads like a field and is computed every time — no stale copy of a price can exist. And __str__ is Lesson 6, holding the intake line format.

self.job = job هو تركيب الدرس 5: فللتذكرة عمل، وهي ليست نوعًا من العمل. وذلك السطر الواحد هو السبب في أن صنف التذكرة نفسه لا يعرف شيئًا عن الشاشات ولا الماء. و_status مع @property للقراءة فقط ودالة advance() واحدة هي تغليف الدرس 3، وهذا هو الجزء الذي يغيّر فعلًا ما يستطيع البرنامج أن يُكسَر به. وquote خاصية @property أيضًا، فتُقرأ كأنها حقل وتُحسب في كل مرة — فلا نسخة قديمة من سعر يمكن أن توجد. و__str__ هي الدرس 6، تحمل صيغة سطر الاستلام.

# ---- the ticket: status is guarded ----------------------------

class Ticket:
    def __init__(self, tid, customer, device, job, priority,
                 technician):
        self.id = tid
        self.customer = customer
        self.device = device
        self.job = job                  # composition
        self.priority = priority
        self.technician = technician
        self._status = "received"       # private on purpose

    @property
    def status(self):
        return self._status

    @property
    def quote(self):
        """Job price plus the urgent surcharge."""
        total = self.job.subtotal()
        if self.priority == "urgent":
            total = total * (1 + URGENT_RATE)
        return total

    def advance(self, new_status):
        """The only door into _status, and it checks."""
        i = STATUS_FLOW.index(self._status)
        allowed = (STATUS_FLOW[i + 1]
                   if i + 1 < len(STATUS_FLOW) else None)
        if new_status != allowed:
            raise ValueError(f"cannot go from {self._status}"
                             f" to {new_status}")
        self._status = new_status

    def __str__(self):
        return (f"{self.id} {self.customer:16}"
                f"{self.device:14}{self.job.kind:8}"
                f"{self.priority:7}{self.quote:8.2f}")

Look at self.job.subtotal() inside quote. The surcharge logic lives in Ticket and the pricing rules live in the job classes, and neither knows the other's code — Ticket never names ScreenJob, and ScreenJob has never heard of a surcharge. That is composition plus polymorphism doing in one line what the structured version did with two functions and a chain, and the difference is not length, it is that Ticket will keep working against job types that do not exist yet.

انظر self.job.subtotal() في داخل quote. فمنطق الزيادة يقيم في Ticket وقواعد التسعير تقيم في أصناف العمل، ولا يعرف أحدهما كود الآخر — فـ Ticket لا يسمّي ScreenJob قط، وScreenJob لم يسمع بزيادة قط. وذلك تركيبٌ وتعدد أشكال يؤدّيان في سطر واحد ما أدّته النسخة البنيوية بدالتين وسلسلة، والفرق ليس الطول، بل أن Ticket سيواصل العمل في مقابل أنواع عمل لم توجد بعد.

And the guard is now real. ticket.status = "collected" does not quietly succeed as the dict version did — the property has no setter, so Python raises AttributeError: property 'status' of 'Ticket' object has no setter and the mistake is a crash on the developer's machine instead of a phone handed over a counter.

والحارس حقيقي الآن. فـ ticket.status = "collected" لا تنجح في صمت كما كانت تنجح نسخة القاموس — فلا setter للخاصية، فترفع بايثون AttributeError: property 'status' of 'Ticket' object has no setter فيكون الخطأ انهيارًا على حاسوب المطوّر لا هاتفًا يُسلَّم فوق منضدة.

Lesson 3. The structured step() checks the transition correctly. Why is the OOP advance() still a stronger guarantee?الدرس 3. تفحص step() البنيوية الانتقال فحصًا صحيحًا. فلِمَ تبقى advance() الكائنية ضمانًا أقوى؟

Encapsulation is not about having a correct check; the structured file has one. It is about there being exactly one way in, so the check cannot be routed around by a developer in a hurry three files away. The third option is the one to be honest about: Python has no real privacy, and ticket._status = "collected" absolutely works if you type it. The difference is that you must type an underscore, which is the language's way of saying "you are now doing something you will have to defend in review" — a convention, but a loud one, and the read path through ticket.status is genuinely read-only because the property has no setter. The first option confuses style with safety, and the fourth is invented: Python checks neither at import time.
التغليف ليس امتلاكَ فحص صحيح؛ فللملف البنيوي فحص. بل هو أن يكون هناك سبيل واحد بالضبط إلى الداخل، فلا يستطيع مطوّر على عجل في ملف ثالث أن يحيد عن الفحص. والخيار الثالث هو الذي يجدر الصدق فيه: فلا خصوصية حقيقية في بايثون، وticket._status = "collected" تعمل قطعًا إن كتبتها. والفرق أنه يجب عليك كتابة شَرْطة سفلية، وهي طريقة اللغة في قول «أنت تفعل الآن شيئًا سيلزمك الدفاع عنه في المراجعة» — عُرْفٌ، لكنه عُرْف عالي الصوت، ومسار القراءة عبر ticket.status للقراءة فقط حقًّا لأن الخاصية لا setter لها. والخيار الأول يخلط الأسلوب بالأمان، والرابع مُختلَق: فبايثون لا تفحص هذا ولا ذاك في وقت الاستيراد.

Lesson 2. kind = "screen" sits in the class body of ScreenJob, not in an __init__. What does that buy?الدرس 2. تقع kind = "screen" في جسد صنف ScreenJob لا في __init__. فماذا يشتري ذلك؟

A class attribute is a fact about the type, not about any one object, so it lives on the class: six tickets in the scenario, and the string "screen" exists once in memory and once in the source. The tempting wrong answer is the third, and it is the one worth being careful about — a class attribute is not read-only. job.kind = "something" on an instance silently creates an instance attribute that shadows the class one for that object only, which is a genuinely confusing bug to chase. If you need it truly fixed, that is what Lesson 3's read-only @property is for. The fourth is simply false: __str__ reads self.job.kind, and attribute lookup checks the instance first and the class second without caring which you wrote.
خاصية الصنف حقيقة عن النوع لا عن كائن بعينه، فتقيم على الصنف: ستّ تذاكر في السيناريو، والنصّ "screen" موجود مرة في الذاكرة ومرة في المصدر. والجواب الخاطئ المغري هو الثالث، وهو الذي يجدر التيقّظ له — فخاصية الصنف ليست للقراءة فقط. فـ job.kind = "something" على حالة تُنشئ في صمت خاصية حالة تحجب خاصية الصنف لذلك الكائن وحده، وهي عِلّة محيّرة حقًّا في تتبّعها. فإن احتجت تثبيتها حقًّا فلذلك وُجدت @property للقراءة فقط في الدرس 3. والرابع كاذب بسادة: فـ __str__ تقرأ self.job.kind، ويفحص البحث عن الخاصية الحالةَ أولًا والصنفَ ثانيًا بلا اهتمام بأيّهما كتبت.
Part 3 — the shop: intake, work log, report (Lessons 1, 2, 6)الجزء 3 — المحل: الاستلام وسجلّ العمل والتقرير (الدروس 1 و2 و6)

Every function in Part 4 of the structured version took tickets as its first parameter. That repeated parameter was the data and its verbs asking to be one thing — which is Lesson 1, the whole reason classes exist. Here they are one thing, and the parameter is gone: it became self.tickets.

أخذت كل دالة في الجزء 4 من النسخة البنيوية tickets معاملها الأول. وكان ذلك المعامل المتكرّر بياناتٍ وأفعالها تطلب أن تكون شيئًا واحدًا — وذلك الدرس 1، وهو كل سبب وجود الأصناف. وها هما شيء واحد هنا، والمعامل ذهب: فقد صار self.tickets.

# ---- the shop: intake, work log, report -----------------------

class RepairShop:
    def __init__(self, name):
        self.name = name
        self.tickets = []

    def intake(self, ticket):
        self.tickets.append(ticket)

    def move(self, tid, new_status):
        """Ask the ticket to move; report its refusal."""
        ticket = next(t for t in self.tickets if t.id == tid)
        try:
            ticket.advance(new_status)
        except ValueError as err:
            print(f"  {tid} -- rejected: {err}")
            return False
        print(f"  {tid} -> {new_status}")
        return True

    def print_intake(self):
        print("intake")
        for t in self.tickets:
            print(f"  {t}")        # __str__ does the work

    def income(self):
        return sum(t.quote for t in self.tickets
                   if t.status == "collected")

    def workload(self):
        load = {}
        for t in self.tickets:
            load[t.technician] = load.get(t.technician, 0) + 1
        return load

    def print_report(self):
        print("daily report")
        print("  tickets per status")
        for s in STATUS_FLOW:
            n = sum(1 for t in self.tickets if t.status == s)
            print(f"    {s:14}{n:2}")
        print(f"  income collected   {self.income():8.2f} ILS")
        load = self.workload()
        busiest = max(load, key=lambda name: load[name])
        print(f"  busiest technician {busiest}"
              f" ({load[busiest]} tickets)")

Two honest observations. First, income, workload and print_report are the same code as before with t["status"] changed to t.status. They were already good; being inside a class did not improve them, and claiming otherwise would be a lie. Second, the division of labour in move is the one real gain here: Ticket.advance decides what is legal and raises, and RepairShop.move decides what to do about a refusal — in this program, print it. A web version of this shop would catch the same ValueError and return a 409 instead, and Ticket would not need a single edit, because it never knew there was a console.

OOP is a tool, not a religionالكائنية أداة لا ديانة

Over-engineering a 30-line script with five classes is a defect, exactly as a 400-line if/elif chain is a defect. class WarrantyRepair(Job):
    """A re-repair of our own work: no fee, parts on us."""

    kind = "warranty"

    def __init__(self, original_job, days_since):
        super().__init__(0.0)
        self.original_job = original_job   # composition
        self.days_since = days_since

    @property
    def in_warranty(self):
        return self.days_since <= 90

    def subtotal(self):
        if self.in_warranty:
            return 0.0
        return self.original_job.subtotal()


jobs = [ScreenJob(180.0),
        BatteryJob(70.0),
        WarrantyRepair(ScreenJob(180.0), days_since=12),
        WarrantyRepair(BatteryJob(70.0), days_since=200)]

for j in jobs:
    print(f"  {j.kind:9}{j.subtotal():8.2f}")

Four lessons are load-bearing in eighteen lines, and no existing class was touched. WarrantyRepair is a Job — inheritance, Lesson 5 — so Ticket accepts it with no edit and the intake table prints it without knowing it exists. It also has a Job — composition, the same lesson — and that is the whole trick: self.original_job.subtotal() works against a screen, a battery, a water job or a future charging-port job, because polymorphism means the held object answers for itself. in_warranty is a @property from Lesson 3, so the 90-day rule is named once and readable as j.in_warranty rather than copied as days <= 90 into every caller. And super().__init__(0.0) is honest bookkeeping: a warranty repair has no parts estimate of its own, and the parent still gets initialised.

Lesson 5. Ticket holds self.job instead of Ticket being subclassed into ScreenTicket, BatteryTicket, WaterTicket. Why is composition right here?الدرس 5. يمسك Ticket بـ self.job بدلًا من أن يُشتقّ Ticket إلى ScreenTicket وBatteryTicket وWaterTicket. فلِمَ كان التركيب صحيحًا هنا؟

The sentence test decides it: "a ticket is a screen job" is false, while "a ticket has a job" is exactly true. The cost of getting it wrong is combinatorial — add urgency as a subclass axis too and you are writing UrgentWaterTicket, six classes for two independent ideas. The fourth option is the trap, because it is a slogan people repeat: this very file inherits three job types from Job and is better for it, since those three really are kinds of the same thing with shared __init__. The third option is false; Job has three subclasses in the file you just read.
